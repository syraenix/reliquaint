# Reliquaint v0.4 Implementation Tasks

> **Status:** Draft, sequenced for Claude Code handoff.
> **Goal:** Render tap-provided companion content (walkthroughs, maps, hints, install notes) alongside catalog entries in the GUI. This is the version that turns Reliquaint into the preservation hub the PRD framed, not just a launcher.

This document breaks v0.4 into milestones, each containing tasks sized for a single Claude Code working session. Each task lists what to do, what to read first, and how to know it's done.

**Reading order before starting any task:** PRD → ADR-0001 → ADR-0002 → ADR-0003 → ADR-0004 → ADR-0005 → ADR-0006 → `schema.md` → `v0.3-tasks.md` (the most recent task list, for codebase context). Each task assumes these are loaded.

ADR-0006 is the critical reference for this version — it defines the security model that constrains every rendering decision. Tasks in Milestones 2 and 3 enforce ADR-0006's policy in code; if implementation pressure surfaces a reason to deviate, raise it in a new ADR rather than relaxing the policy ad-hoc.

## Milestone 1 — Companion content discovery and indexing

Get the launcher to know what companion content exists for each game across all subscribed taps.

### Task 1.1: Companion directory conventions

Document and implement the on-disk layout for companion content within a tap.

- Layout: `<tap-root>/companion/<game-id>/` contains files for that game's companion content.
- Recognized file types:
  - `.md` — Markdown content (walkthroughs, hints, install notes, overviews).
  - `.png`, `.jpg`, `.jpeg`, `.gif`, `.webp` — images referenced from Markdown. **SVG is explicitly excluded** per ADR-0006.
- File naming conventions:
  - Numeric prefix sorts: `01-overview.md` before `02-walkthrough.md`. Filenames without numeric prefixes sort alphabetically after numeric-prefixed files.
  - Title derived from filename: prefix stripped, hyphens/underscores become spaces, words capitalized. `01-walkthrough.md` → "Walkthrough"; `boss-fight-tips.md` → "Boss Fight Tips".
- Subdirectories: `companion/<game-id>/hints/` and `companion/<game-id>/maps/` are first-class groupings; the launcher treats subdirectory names as section labels.
- No `companion.toml` index file for v0.4. Directory walking with the above conventions is sufficient; revisit if explicit ordering or title overrides become needed.
- Update `docs/schema.md` to document the companion directory layout and the file/sorting/grouping conventions.

**Done when:** A test tap with a populated `companion/<game-id>/` directory is parsed correctly: ordering matches numeric prefixes, titles derive from filenames, subdirectories group content.

### Task 1.2: Companion content indexer

Build the in-memory index of companion content alongside the catalog load.

- For each subscribed tap (including the `local` user tap), walk `companion/` and build an index keyed by `(tap_id, game_id) -> Vec<CompanionItem>`.
- A `CompanionItem` carries: relative path within the tap, title, kind (markdown or image), and section/group (root or a subdirectory name).
- Indexing happens at catalog assembly time per v0.1 Task 2.3's `CatalogView`. Extend that view with a `companion_for(game_id)` accessor returning items across all subscribed taps.
- Errors loading individual files (unreadable, malformed) log a WARN and skip that item; they do not fail the indexer.

**Done when:** A test confirms `companion_for(game_id)` returns aggregated items from multiple taps with correct ordering and attribution.

### Task 1.3: Multi-tap aggregation rules

Define what happens when multiple taps provide companion content for the same game.

- Items from different taps are not conflicts. They aggregate — the user sees all of them.
- Order within a game's companion view: items grouped by tap (priority-ordered per v0.3 Task 3.2's subscription priority), then by the v0.3 file-ordering conventions within each tap.
- Each `CompanionItem` retains its tap-of-origin for attribution display in the GUI.

**Done when:** Two taps shipping companion content for the same game produce a combined view where each item is correctly attributed to its source tap.

## Milestone 2 — Rendering pipeline

Server-side Markdown rendering, HTML sanitization, and the tap-local image protocol. Everything in this milestone is in the Rust backend; the webview consumes only the sanitized output.

### Task 2.1: Markdown rendering

Integrate `pulldown-cmark` to render Markdown to HTML in the launcher backend.

- Add `pulldown-cmark` as a workspace dependency.
- **Disable raw HTML passthrough** in the parser options. This is the critical security configuration — without it, the rest of the sanitizer is significantly compromised.
- Enable: tables, footnotes, strikethrough, task lists. These are useful for walkthrough content.
- Render to an HTML string.
- Unit tests covering: paragraphs, headings, lists, code blocks (fenced and inline), tables, links, images, footnotes, and a deliberately-malicious input with embedded `<script>` to confirm it's stripped at the parse stage before sanitization even runs.

**Done when:** Markdown renders to HTML with the expected features; raw HTML in the source is escaped, not passed through.

### Task 2.2: HTML sanitization

Add `ammonia` and configure the strict whitelist per ADR-0006.

- Add `ammonia` as a workspace dependency.
- Configure the whitelist explicitly:
  - Tags: `p`, `em`, `strong`, `code`, `pre`, `blockquote`, `h1` through `h6`, `ul`, `ol`, `li`, `a`, `img`, `table`, `thead`, `tbody`, `tr`, `th`, `td`, `hr`, `br`, `del`, `input` (for checkbox-only task lists, with strict attribute filtering).
  - Allowed attributes: `href` on `<a>` (with URL scheme allowlist: `http`, `https`, `reliquaint-content`, plus relative paths), `src` and `alt` on `<img>` (same scheme allowlist), `type` and `checked` on `<input>` (only for task lists, with `type="checkbox"` enforced).
  - **Disallowed:** `style`, `class`, `id`, `srcset`, all event handlers (`onclick` etc.), `<script>`, `<style>`, `<iframe>`, `<object>`, `<embed>`, `<form>`, `<svg>`.
- Sanitize the output of Task 2.1 before it crosses to the webview.
- Tests against common XSS payloads from cheat sheets — every one should be neutralized.

**Done when:** A corpus of malicious Markdown inputs (event handlers, `javascript:` URLs, embedded HTML, data-URI images, `<style>` blocks) all sanitize to safe output. Test cases live in the codebase as documentation of the threat model.

### Task 2.3: Tap-local image protocol handler

Implement a custom Tauri protocol that serves images from within tap cache directories.

- Protocol name: `reliquaint-content://`
- URL shape: `reliquaint-content://<tap-id>/<game-id>/<relative-path>`
- The handler resolves to `<tap-cache>/<tap-id>/companion/<game-id>/<relative-path>` and serves the file.
- **Path-traversal protection:** validate the resolved path stays within `<tap-cache>/<tap-id>/companion/<game-id>/` after symlink resolution. Reject any access outside this boundary with a 403-equivalent.
- **Format check:** validate the file's extension matches the allowed image set (PNG, JPEG, GIF, WebP). Reject anything else, including files whose magic bytes don't match their extension.
- Return appropriate MIME types in response headers.
- Tests covering: legitimate access, `..` traversal attempt, absolute path attempt, symlink escape attempt, format mismatch.

**Done when:** A legitimate image URL serves the file; every attempted boundary violation returns an error and is logged at WARN with the attempting tap and path.

### Task 2.4: Link rewriting

Markdown links and image sources need URL rewriting between Tasks 2.1 and 2.2.

- **Image `src` attributes** with relative paths get rewritten to `reliquaint-content://<tap-id>/<game-id>/<path>` so they resolve via the protocol from Task 2.3.
- **Link `href` attributes**:
  - `http://` and `https://` URLs pass through; the webview's click handler (Milestone 3) intercepts and opens in the system browser.
  - Relative paths to other Markdown files within the same `companion/<game-id>/` directory are rewritten to internal-navigation links the webview can handle.
  - Everything else (`javascript:`, `data:`, `file:`, `mailto:`, etc.) is stripped by `ammonia`'s scheme allowlist from Task 2.2.

**Done when:** A Markdown file referencing both `![map](maps/spielburg.png)` and `[next section](02-mid-game.md)` renders with the image src rewritten to the protocol URL and the link rewritten to an internal-navigation form.

## Milestone 3 — GUI companion content

User-facing rendering of the indexed and sanitized content.

### Task 3.1: "Guides" section on game detail view

Add a section to the existing game detail view that surfaces companion content.

- Section header: "Guides" (or "Companion content" — implementer's call based on what reads naturally in the existing layout).
- Lists available companion items grouped by tap, then by section (root, hints, maps, etc.).
- Each item shows its title and an icon indicating its kind (markdown or image).
- Clicking an item opens the content view (Task 3.2).
- Empty state when no companion content exists for the game: a quiet message ("No guides available for this game yet."), no banner shouting.

**Done when:** A game with companion content shows the list; a game without shows the empty state; navigation to a content item works.

### Task 3.2: Markdown content viewer

Render the sanitized HTML from Milestone 2 in the webview.

- Display the rendered HTML inside a viewer pane that lives within the game detail view (not a separate window).
- Apply the launcher's color palette to the rendered content per the `colors.css` styling — headings use `--gold`, body text uses `--text-primary`, code uses `--bg-elevated` with `--text-primary`, blockquotes get a subtle `--burgundy` left border, etc.
- Implement the link-click handler:
  - External (`http`, `https`): intercept and open in the system browser via Tauri's `shell.open`.
  - Internal (relative, rewritten in Task 2.4): navigate to the linked content within the viewer.
- A "Back to game" link or breadcrumb returns to the detail view.

**Done when:** Loading a Markdown guide renders it correctly styled, external links open in the browser, internal links navigate within the viewer, and the back path returns to the detail view.

### Task 3.3: Image viewing

Images embedded in Markdown render inline; clicking opens a zoomable view.

- Inline rendering at a reasonable max width that fits the content viewer pane.
- Click-to-zoom opens a modal/lightbox view with the full-resolution image.
- Modal supports: keyboard close (Esc), click-outside-to-close, and basic pan if the image is larger than the viewport. Full zoom controls are a v0.5 nice-to-have; v0.4 minimum is "see the image at full resolution."

**Done when:** A Markdown file containing `![map](maps/spielburg.png)` shows the image inline at fit-width, clicking opens a larger view, and dismissal works.

### Task 3.4: Multi-tap attribution

Make the tap-of-origin visible for each piece of companion content.

- In the Guides list (Task 3.1), each content item displays a small "from <tap-name>" badge.
- In the content viewer (Task 3.2), the current item's tap is shown in the header alongside the item's title.
- Multiple-tap groupings in the Guides list are visually distinct, with a section header per tap.

**Done when:** A test scenario with two taps providing companion content for the same game shows clearly which tap each item came from in both the list and the viewer.

## Milestone 4 — Polish

### Task 4.1: Companion content in the local user tap

The local user tap (from v0.2) can also carry companion content. Users adding their own notes to a game put files in `${XDG_CONFIG_HOME}/reliquaint/tap/companion/<game-id>/`.

- The indexer from Task 1.2 already handles this if the loader treats `local` as just another tap. Verify and add tests.
- User-tap companion content is attributed as "from your local tap" or similar — distinguish from subscribed taps in the GUI.

**Done when:** A user-tap companion entry appears alongside subscribed-tap content with the right attribution.

### Task 4.2: Doctor checks for companion content

Extend the `doctor` command from v0.1 to check companion content health.

- For each game with installation records: do any companion-content image references point at files that don't exist?
- For each subscribed tap: are there `companion/<game-id>/` directories for games not in the tap's catalog? (Probably a tap maintainer typo; warn.)
- For each companion Markdown file: did sanitization strip a significant amount of content? (Possible indication of a tap submitting raw HTML expecting it to render; warn so users know what they're not seeing.)

**Done when:** A deliberately broken companion entry surfaces in `doctor` output with an actionable message.

### Task 4.3: Performance pass

Verify the rendering pipeline handles real-world content sizes acceptably.

- Test against a corpus of typical walkthrough content (~5–20 KB Markdown plus a handful of images per game).
- Measure cold-load time for the largest companion entry in `reliquaint-core` at the time of implementation.
- Add tracing spans around: companion indexing, Markdown rendering, image protocol serving. These help future profiling if performance becomes a concern.
- If any single operation exceeds a reasonable budget (~100ms cold), document the bottleneck and decide whether to address now or defer.

**Done when:** Performance baseline is documented; tracing instrumentation is in place; no operation noticeably blocks the UI during typical use.

**Implementation note (v0.4):** `info_span!` instrumentation is in place on the three hot
paths — `companion::index_companion` (`companion_index`), `companion_render::render_markdown`
(`companion_render`, with `in_bytes`/`out_bytes`), and `companion_protocol::resolve_image_in`
(`companion_image`). The spans are zero-cost when no subscriber is attached; to read timings,
run with span events enabled, e.g. `RUST_LOG=reliquaint=debug reliquaint …` (the CLI) or the
GUI diagnostic panel. A concrete cold-load baseline for the largest `reliquaint-core` entry is
deferred until that tap ships companion content — there is nothing real to measure against
yet. The pipeline is pure Rust and synchronous per request (no caching for v0.4, per
ADR-0006); for the expected ~5–20 KB walkthrough sizes, render is well under the ~100 ms
budget. Revisit with real numbers once `reliquaint-core` companion content exists.

## Out of scope for v0.4

Documented so reviewers and contributors can redirect noise:

- **PDF rendering** for scanned manuals. Genuinely valuable preservation content; needs its own ADR (covering PDF parser choice, security model, viewer UX). Likely a v0.5 conversation.
- **Video and audio content** in companion sections. No clear path yet; no demand to drive it.
- **Full-text search across companion content.** Useful but a significant addition. Catalog-level search isn't even in yet.
- **In-app editing of companion content.** The maintenance workflow stays git-based; users edit Markdown in their editor of choice and submit PRs.
- **A `companion.toml` index file** for explicit ordering and title overrides. Directory conventions handle the common case; revisit if explicit metadata becomes necessary.
- **Remote image URLs** in companion content. Closed in ADR-0006 on privacy and security grounds.
- **SVG image support.** Closed in ADR-0006 on security grounds.
- **HTML pass-through, even with sanitization.** Closed in ADR-0006.
- **Allow-listed HTML for curated/trusted taps.** Speculative; revisit only if a clear need emerges from `reliquaint-core` maintenance.
- **Annotation systems** (user-attached notes to games). Adjacent feature, different scope.
