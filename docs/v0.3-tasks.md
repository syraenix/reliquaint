# Reliquaint v0.3 Implementation Tasks

> **Status:** Draft, sequenced for Claude Code handoff.
> **Goal:** Implement tap subscription so the launcher can read from multiple catalog sources, extract `reliquaint-core` from the launcher repository to its own home, and lay the groundwork for the community-contribution distribution model per ADR-0003.

This document breaks v0.3 into milestones, each containing tasks sized for a single Claude Code working session. Each task lists what to do, what to read first, and how to know it's done.

**Reading order before starting any task:** PRD → ADR-0001 → ADR-0002 → ADR-0003 → ADR-0004 → ADR-0005 → `schema.md` → `v0.1-tasks.md` → `v0.2-tasks.md`. Each task assumes these are loaded.

v0.3 is the first version that touches **two repositories**: the launcher (`syraenix/reliquaint`) and the soon-to-be-extracted core tap (`syraenix/reliquaint-core`). Tasks call out which repository each change lands in.

---

## Milestone 1 — Tap registry

The data model and persistence layer for tap subscriptions. No fetching or loading yet — just the registry of "what is the user subscribed to."

### Task 1.1: Subscription manifest

User subscriptions live in a single TOML file the launcher reads at startup and writes whenever subscriptions change.

- Location: `${XDG_CONFIG_HOME:-$HOME/.config}/reliquaint/subscriptions.toml`
- Schema:
  ```toml
  schema_version = 1

  [[tap]]
  id        = "reliquaint-core"
  source    = "https://github.com/syraenix/reliquaint-core"
  added_at  = 2026-06-01T12:00:00Z
  priority  = 0   # lower wins in conflicts
  ```
- Subscriptions are ordered: lower `priority` wins when two taps offer the same `game_id`. The `local` user tap (from v0.2) is always present and not listed in this file; it has an implicit priority that places it above subscribed taps (the user's own definitions win).
- Validation: tap ids must be unique across the file. The reserved id `local` is rejected.
- Update `docs/schema.md` to document this file alongside the existing schemas.

**Done when:** A unit test writes and reads a subscriptions manifest round-trip; duplicate ids and reserved-id violations are rejected with clear errors.

### Task 1.2: Tap storage layout

Fetched taps cache to a known on-disk layout.

- Location: `${XDG_DATA_HOME:-$HOME/.local/share}/reliquaint/taps/<tap-id>/`
- Contents inside each tap directory mirror the layout in `schema.md` §"Tap layout": `tap.toml` at root, `catalog/<platform>/*.toml`, sibling configs.
- The tap directory is owned by the launcher; users should not hand-edit fetched taps (warn if a tap's git status is dirty on sync).
- Path helpers go in the existing `paths` module from v0.1 Task 1.6.

**Done when:** Path helpers expose `tap_cache_dir()` and `tap_cache_dir_for(tap_id)`, neither hardcoded outside the helpers module.

### Task 1.3: Known-tap short names

Built-in resolution table for official tap short names.

- A small Rust constant or static map: `{"reliquaint-core" -> "https://github.com/syraenix/reliquaint-core"}`.
- Used by `tap add <name>` to resolve a bare short name to a URL when the input doesn't look like a URL or path.
- Extensible by editing the source; deliberately not user-configurable in v0.3. Future versions may add a resolution registry.

**Done when:** `tap add reliquaint-core` resolves to the canonical URL; `tap add https://example.com/foo` is treated as a literal URL; `tap add ./local-tap` is treated as a local path (for testing).

## Milestone 2 — Tap fetching

Implement the actual network operations.

### Task 2.1: Git availability check

The launcher uses system `git` for fetching. Verify it's available on `$PATH` at startup and fail fast with a clear error if not.

- Add to `doctor` checks: presence of `git`, version (any reasonably modern release).
- Surface a clear actionable error if missing: "Reliquaint needs `git` to fetch taps. Install it with `apt install git` or your distro equivalent."

**Done when:** `reliquaint doctor` reports git presence; running `tap add` without git available produces the actionable error rather than a panic.

### Task 2.2: Git clone implementation

Fetch a tap from a git URL into the cache.

- Shell out to `git clone --depth=1 <url> <cache-dir>`.
- Capture stdout/stderr through `tracing` at DEBUG so users can see what happened on `-v`.
- On failure, leave the cache directory in a clean state — partial clones must be removed before the error returns.
- A 5-minute hard timeout on the clone; configurable via user config later if needed.

**Done when:** A test against a known public git URL (use a small fixture repo) clones successfully; an invalid URL fails cleanly with no leftover directory.

### Task 2.3: Git pull implementation

Update an already-cached tap to the latest commit on its default branch.

- Shell out to `git -C <cache-dir> pull --ff-only`. Fast-forward only — refuse to merge or rebase on unexpected upstream history rewrites.
- If the user has somehow modified the cache (dirty working tree, divergent local commits), warn but do not overwrite. Suggest `tap remove` and `tap add` to start fresh.
- Capture the before-and-after commit hashes for reporting.

**Done when:** `tap sync` on a known tap that has new commits pulls them; a tap with no new commits reports "up to date"; a dirty cache produces a warning rather than data loss.

### Task 2.4: Tap content validation

After fetching, validate the tap's structure before adding it to the catalog.

- `tap.toml` must be present, parse cleanly, and have the correct `schema_version`.
- The `tap.toml` `id` field must match either the user-supplied id (when adding) or the previously-stored id (when syncing). Mismatch on sync produces a warning and does not change the local id.
- Walk `catalog/<platform>/*.toml`; each file must parse cleanly. Individual failures log a WARN and skip that entry; only `tap.toml` failure is fatal to the tap.
- Path traversal check on `config` and `floppies` field references — they must be plain filenames, not paths with components like `..` or absolute paths.
- Validation runs against the **cache directory contents**, not the live catalog state.

**Done when:** A malformed tap (missing `tap.toml`, bad schema version, path traversal attempt) is rejected with clear errors before being registered; a tap with one bad catalog entry registers successfully with a WARN about the bad entry.

## Milestone 3 — Catalog loading from subscribed taps

Extend the v0.1/v0.2 catalog assembly to read from subscribed taps too.

### Task 3.1: Multi-tap loader extension

Generalize the catalog loader (v0.1 Task 2.1 as extended in v0.2 Task 1.2) to read from every subscribed tap plus the `local` user tap.

- For each subscribed tap in the registry, walk its cache directory and load catalog entries.
- Combine into a single in-memory catalog keyed by `(tap_id, game_id)`, same shape as the existing `CatalogView`.
- A subscribed tap that fails to load entirely (cache directory missing, fatal validation) appears in the registry but reports a "broken" status; its entries are absent from the view.

**Done when:** Subscribing to a test tap, running `reliquaint list`, and seeing the test tap's games appear alongside the `local` tap's entries.

### Task 3.2: Conflict resolution by priority

When the same `game_id` appears in multiple taps, the lowest-priority value wins for the default view. Other versions remain accessible by explicit `(tap_id, game_id)` lookup.

- The `CatalogView` exposes both `by_game_id(id) -> winner` (priority-resolved) and `all_with_game_id(id) -> Vec<Entry>` (all versions).
- Install records continue to be keyed by `(tap_id, game_id)`, so the user's existing installs always resolve to the specific catalog entry they were originally installed against, regardless of priority changes.
- The CLI's `list` shows the resolved winner; a `--show-conflicts` flag enumerates duplicates.

**Done when:** Two taps both shipping `qfg1-ega` produce a single entry in `list` output (the priority winner); `--show-conflicts` shows both; an installed copy keeps pointing at its original tap regardless of priority changes.

### Task 3.3: Orphan installation handling

When a user has installation records pointing at `(tap_id, game_id)` that the launcher can't find — typically because they unsubscribed from a tap or upgraded from v0.2 without subscribing to `reliquaint-core` — surface this clearly.

- The `CatalogView` already exposes orphans via v0.1 Task 2.2's mechanism. Extend the error message to specifically suggest `tap add <tap-id>` when the missing tap matches a known short name.
- `doctor` lists orphans with the same actionable suggestion.

**Done when:** A user with installation records pointing at `reliquaint-core` but no subscription to it sees "Subscribe to `reliquaint-core` with `reliquaint tap add reliquaint-core`" in both `list` output and `doctor` output.

## Milestone 4 — CLI tap commands

### Task 4.1: `reliquaint tap add <name-or-url>`

Subscribe to a new tap.

- Resolves short names via Task 1.3 lookup; otherwise treats input as a URL or local path (local paths for testing only).
- Fetches via Task 2.2.
- Validates via Task 2.4.
- Writes to the subscriptions manifest.
- Prints what was added and the count of catalog entries it provided.
- `--priority N` flag sets explicit priority; default is "append to end" (highest priority number among existing entries plus one).

**Done when:** `reliquaint tap add reliquaint-core` end-to-end results in `reliquaint list` showing the core tap's games.

### Task 4.2: `reliquaint tap remove <id>`

Unsubscribe from a tap.

- Removes from the subscriptions manifest.
- Deletes the cache directory.
- Refuses to operate on the `local` id (the user tap is structural, not subscribed) with a clear error.
- Warns if removal would orphan installation records, listing the affected games. Prompts for confirmation unless `--force`.

**Done when:** Removing a tap with installs produces the warning; confirming proceeds with the removal; the cache directory is gone afterward.

### Task 4.3: `reliquaint tap list`

Show subscribed taps with status.

- Columns: id, source URL, priority, last synced, status (ok / broken / out of date if upstream has newer commits and a `--check-remote` flag is passed).
- `--format json` for scripting.
- Includes the `local` user tap as a row with source = "(user)" and no remote status.

**Done when:** Manual run shows subscribed taps clearly; the user tap appears alongside subscribed taps but distinguishably.

### Task 4.4: `reliquaint tap sync`

Update one or all subscribed taps.

- With no arguments: syncs all subscribed taps.
- With a tap id: syncs just that one.
- Reports per-tap: commits pulled, entries added/changed/removed (diff against the pre-sync state).
- Continues past per-tap failures and reports them at the end.

**Done when:** Running `tap sync` against a tap with new upstream commits pulls them and reports the catalog-entry delta.

### Task 4.5: `reliquaint tap reorder`

Change tap priority.

- `reliquaint tap reorder <id> --priority N` sets a tap's priority explicitly.
- `reliquaint tap reorder --interactive` (or `-i`) opens `$EDITOR` on a small text representation of the ordering for the user to rearrange.
- Validation: priorities don't need to be contiguous, but no two taps may share a priority.

**Done when:** Reordering changes which tap wins conflict resolution in `list` output without affecting which tap an installed copy points at.

## Milestone 5 — GUI tap management

### Task 5.1: First-run subscription prompt

When the launcher GUI opens with no subscriptions in `subscriptions.toml`, show a welcome screen rather than an empty catalog.

- Title: "Welcome to Reliquaint."
- Body: "To get started, subscribe to a tap — a curated catalog of games. The official Reliquaint Core tap covers a starter set of classic DOS and Amiga titles."
- Primary action: "Add Reliquaint Core" button. Shows the URL it will fetch (`https://github.com/syraenix/reliquaint-core`) for transparency before adding.
- Secondary action: "I'll add a tap later" — dismisses to the empty catalog state.
- The empty-catalog state itself shows a non-blocking banner with the same suggestion.

**Done when:** First launch shows the welcome screen; clicking the primary button subscribes and the catalog appears; dismissing leaves an empty catalog with a banner.

### Task 5.2: Tap management settings panel

A new settings panel for managing subscriptions.

- Reachable from the top bar (perhaps a "Taps" button alongside "Doctor", or as part of a broader settings panel — implementer's call).
- Lists subscribed taps with: name (title from `tap.toml`), URL, priority, last synced, entry count, status indicator.
- Actions per tap: sync, remove, edit priority. The `local` user tap appears at the top with a "(your custom games)" label and only an "open folder" action.
- A "+ Add tap" button at the top opens an inline form: short name or URL, optional priority. Submitting fetches and validates.

**Done when:** Adding, removing, syncing, and reordering taps via the panel all produce the same effects as the CLI equivalents; the catalog browser updates immediately when subscriptions change.

### Task 5.3: Tap-of-origin badging in catalog browser

Make the tap each game comes from visible at a glance.

- Subtle tap label on each game card next to the platform badge: `core`, `local`, or the tap's id (truncated if long).
- Detail view's metadata table already shows the tap field; keep that.
- A filter chip at the top of the catalog: "All taps" / "<tap-name>" — lets the user view one tap at a time.

**Done when:** Cards show their tap of origin; filtering by tap works.

### Task 5.4: Conflict resolution UI

When the same game appears in multiple subscribed taps, the GUI shows the resolution clearly.

- Detail view shows "Also in: <other-tap-name>" beneath the metadata table when alternates exist.
- Clicking that opens the alternate entry.
- A "Make this version the default" button changes priority such that the currently-viewed tap wins.

**Done when:** A test scenario with two taps shipping the same game can be navigated end-to-end, including switching which one is the default.

## Milestone 6 — Core tap extraction

The big migration. Works alongside Milestones 1–5; the final switch lands at the end of v0.3.

### Task 6.1: Create the `reliquaint-core` repository

In a new repository at `https://github.com/syraenix/reliquaint-core`:

- Initialize with: `README.md`, `LICENSE` (CC-BY-SA-4.0 to match `LICENSE-CONTENT` from the launcher repo), `CODE_OF_CONDUCT.md`, `CONTRIBUTING.md` tailored to tap maintenance (not launcher development), `.github/` with CI that runs schema validation against every catalog entry.
- The CI workflow should be simple: install the latest released `reliquaint` binary (or build from source if needed), run a validation command against every TOML file in `catalog/`, and fail on any error.
- Repository description, topics, etc. similar to the launcher repo but scoped to "Official catalog content."

**Done when:** The new repo exists, has its community files in place, and CI passes against an empty `catalog/` tree.

### Task 6.2: Move tap content

Move the contents of `tap/` from the launcher repo to the `reliquaint-core` repo.

- File-level move preserving git history is preferred where practical (e.g., via `git filter-repo` or by copying with `git log --follow` traces). If history preservation is too complex, a single clean import commit citing the launcher repo's source commit is acceptable — note this in the new repo's first commit message.
- Update internal references: any `tap/catalog/...` references in catalog content (none expected, but worth grepping) become root-relative.
- Tag the new repo `v0.1.0` once the content is in to give the launcher something stable to point at.

**Done when:** The new repo contains all 18 catalog entries with their sibling configs; CI passes.

### Task 6.3: Validation command

The launcher needs a CLI subcommand that the `reliquaint-core` repo's CI can use.

- `reliquaint tap validate <path>` — runs the same validation as Task 2.4 against a local directory rather than a fetched cache.
- Exit code 0 on success, non-zero on failure with each failure printed clearly.
- Can be run against the in-repo tap before adding entries.

**Done when:** Pointing the new repo's CI at its own checkout runs the validation cleanly; introducing a deliberate error fails CI.

### Task 6.4: Switch launcher to subscribe

The cutover in the launcher repo:

- Remove the bundled `tap/` directory from the launcher repo.
- Update CI and release workflows to no longer ship bundled tap content.
- Update the launcher's startup behavior: with no subscriptions, no bundled content shows — the first-run prompt from Task 5.1 takes over.
- A migration helper for existing v0.2 users: `reliquaint upgrade` detects if installation records reference `reliquaint-core` but no subscription exists, prompts to subscribe.
- Release notes for v0.3 must explicitly call out this change.

**Done when:** A clean v0.3 install with no prior state shows the first-run prompt; an upgrade from a v0.2 install with existing installs shows the upgrade helper.

## Cross-cutting concerns worth flagging

**Two-repo coordination.** Milestone 6 happens across both repositories. The order is: stand up `reliquaint-core` (6.1, 6.2), implement validation (6.3), then switch the launcher (6.4). Don't merge 6.4 to the launcher's main branch until the new repo is live and tagged.

**Release timing.** The launcher v0.3.0 release and the `reliquaint-core` v0.1.0 release should land within a short window of each other. If the launcher ships first, users have nothing to subscribe to. If the core tap ships first, existing v0.2 users have a working setup that the launcher hasn't been told about yet.

**Testing without the external repo.** Most of Milestones 1–5 can be developed and tested against `file://` URLs or local paths pointing at the launcher repo's existing `tap/` directory. Only the final switch in 6.4 requires the external repo to exist.

## Out of scope for v0.3

- **Tarball-based fetching.** Git only for v0.3. Tarball support is mechanically simple to add later as an alternative fetch transport in Milestone 2.
- **Tap signing or verification.** Users trust taps they explicitly subscribe to. Cryptographic signing is a real future concern but adds significant complexity (key management, distribution, revocation) that v0.3 should not take on.
- **In-launcher tap discovery / search.** Finding good third-party taps relies on docs and community word-of-mouth for v0.3. A future "awesome-reliquaint-taps" repository or in-launcher registry can come later.
- **Versioned pinning.** `tap sync` always pulls the latest commit on the default branch. Pinning a tap to a specific version or commit is a future addition.
- **Branch selection.** Taps fetch from the default branch only.
- **Authenticated fetching.** Public HTTPS git URLs only. SSH and credentialed HTTPS need a credential-handling story that's out of v0.3 scope.
- **Companion content rendering.** Still v0.4.
