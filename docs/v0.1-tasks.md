# Reliquaint v0.1 Implementation Tasks

> **Status:** Complete — all v0.1 tasks have shipped. Kept for historical context.
> **Goal:** Refactor Reliquaint to the two-layer manifest model with split emulator configs, ship the bundled `reliquaint-core` tap, and reach public-ready foundation per the PRD's v0.1 phase.

This document breaks v0.1 into milestones, each containing tasks sized for a single Claude Code working session. Each task lists what to do, what to read first, and how to know it's done.

Tasks are sequenced by dependency. Within a milestone, tasks can sometimes run in parallel; cross-milestone dependencies are noted explicitly.

**Reading order before starting any task:** PRD → ADR-0001 → ADR-0002 → ADR-0003 → ADR-0004 → ADR-0005 → `schema.md`. Each task assumes these are loaded.

---

## Milestone 1 — Data model

The TOML types the rest of the launcher reads and writes, plus the logging foundation everything else will use.

### Task 1.1: Logging infrastructure

Set up the `tracing` ecosystem per ADR-0004 before any other code lands. Subsequent tasks instrument their work using the patterns established here.

- Add `tracing` and `tracing-subscriber` as workspace dependencies.
- Initialize a default subscriber in both binary entry points (CLI `main`, Tauri `setup`).
- Wire `EnvFilter` to honor `RUST_LOG`.
- Add `-v` / `-vv` CLI flags that elevate the filter to `DEBUG` / `TRACE` respectively.
- Stub the Tauri-side subscriber layer that forwards events to the frontend, even if the frontend doesn't consume them yet — Milestone 5 will wire the panel.
- Establish coding conventions in code comments or a `CONTRIBUTING.md` stub: when to use which level, when to open a span vs. emit an event, what structured fields to include.

**Done when:** `reliquaint list -v` produces formatted debug-level output to stderr, `RUST_LOG=trace reliquaint list` produces trace output, and the GUI binary boots without panicking on the stubbed subscriber layer.

### Task 1.2: Error handling foundation

Set up the error-handling patterns per ADR-0005 before the parser tasks land. Subsequent parser tasks add their domain-specific error enums on top of the conventions established here.

- Add `thiserror` and `anyhow` as workspace dependencies.
- Define a top-level `ReliquaintError` enum in an `error` module. It may start empty; subsequent parser tasks add variants via `#[from]` as they're written.
- Install a custom panic hook at both binary entry points (CLI `main`, Tauri `setup`) that prints a brief "please file a bug" message and a pointer to capturing trace-level logs before re-panicking.
- Document conventions in code comments or a `CONTRIBUTING.md` stub: per-module `thiserror` enums, no `anyhow` in library code, no library-side error logging, panic policy.

**Done when:** The crate compiles with the new dependencies, the panic hook is wired and demonstrably catches a deliberate `panic!()` in a test binary, and the `error` module exposes the top-level type subsequent tasks can extend.

### Task 1.3: Catalog entry types and parser

Add a `catalog` module under `launcher/src-tauri/src/` (or fold into the existing `manifest` module — implementer's call) with Rust types matching the catalog entry schema in `schema.md`.

- Use `serde` + the existing TOML dependency.
- Cover all subtables: `game`, `meta`, `acquisition`, `install`, `runtime`, `runtime.dosbox`, `runtime.fs_uae`.
- Reject `schema_version != 1` with a clear error.
- Validate the id format (`^[a-z][a-z0-9-]*[a-z0-9]$`) at parse time.
- Validate platform/runtime consistency: `platform = "dos"` requires `[runtime.dosbox]`, etc.
- Instrument parse errors with `tracing::error!` carrying the file path as a structured field.

**Done when:** A unit test loads a fixture catalog entry for both a DOS game (QFG1 EGA) and an Amiga game (Fatman), and the round-tripped TOML matches semantically.

### Task 1.4: Installation record types and parser

Add an `install` module (or fold into `manifest` — same call) with Rust types matching the installation record schema.

- Serde-based read and write.
- Validate that `install_path` exists and is a directory at load time? **No** — record load is read-only and shouldn't fail on missing directories (the user may have unplugged a drive). The `doctor` command and launch path handle absence with clear errors.
- Expand `~` in `install_path` at read time only if present; written records use absolute paths.

**Done when:** A unit test writes and reads an installation record round-trip. Loading a record pointing at a nonexistent path returns the record without error; downstream code is responsible for checking path existence.

### Task 1.5: Tap metadata types and parser

Types for `tap.toml`.

- Same pattern as 1.1 and 1.2.
- Validate the tap id format.
- Reject duplicate-id taps at the layer that loads them (Task 2.1).

**Done when:** A unit test loads the bundled tap's `tap.toml` and exposes its fields.

### Task 1.6: Path constants and helpers

Centralize all path resolution in a `paths` module (one likely already exists per the current code structure; extend it).

- `tap_root()` — where the bundled tap lives.
- `user_taps_dir()` — `${XDG_DATA_HOME}/reliquaint/taps/` for v0.3 future use; create the constant now so it isn't hardcoded later.
- `installs_dir()` — `${XDG_DATA_HOME}/reliquaint/installs/`.
- `user_config_path()` — `${XDG_CONFIG_HOME}/reliquaint/config.toml`.

All XDG resolution honors the environment variables and falls back to the documented defaults (`~/.local/share`, `~/.config`).

**Done when:** No path string outside this module references `.local/share` or `.config` directly.

## Milestone 2 — Tap loading and catalog assembly

### Task 2.1: Bundled tap discovery and loading

Walk the bundled tap directory, parse `tap.toml`, then load every `catalog/<platform>/*.toml`.

- Build an in-memory `Catalog` keyed by `(tap_id, game_id)`.
- Reject duplicate game ids within the same tap with a clear error pointing at both files.
- Surface parse errors with file path and line context (serde-toml provides this; just don't swallow it).
- Skip files starting with `_` or `.` so contributors can stash drafts in the tap tree without breaking startup.

**Done when:** `reliquaint list` enumerates every game in the bundled tap and exits cleanly even if some entries fail to parse (failing entries log a warning and are skipped, not fatal).

### Task 2.2: Installation record loading

Scan the installs directory and load all records.

- Build an in-memory map of `(tap_id, catalog_id) -> InstallRecord`.
- Records pointing at unknown `(tap_id, catalog_id)` are loaded but flagged; the GUI/CLI can show them as orphaned.
- Records that fail to parse log a warning and are skipped.

**Done when:** A test creates two installation records (one valid, one with an unknown catalog id), runs the loader, and confirms both are present in the result with the right flags.

### Task 2.3: Catalog + install join

A `CatalogView` type that joins catalog entries with their installation records (or absence thereof) at startup.

- For each catalog entry, attach the matching installation record or `None`.
- Expose query methods the CLI and GUI both use: `all()`, `by_id(id)`, `by_platform(p)`, `installed_only()`, `not_installed()`.
- Orphaned installation records (no matching catalog entry) are exposed via a separate `orphans()` accessor; the GUI surfaces them with a "your tap may have been removed" message.

**Done when:** A test loads a fixture catalog and a fixture set of installation records and asserts the join is correct.

## Milestone 3 — Emulator launch composition

### Task 3.1: User launcher config loader

Parse the user's `${XDG_CONFIG_HOME}/reliquaint/config.toml` per the schema doc.

- Missing file is fine; treat as all-defaults.
- Bake in Debian-friendly defaults: `flatpak run io.github.dosbox-staging` for DOSBox-Staging, `fs-uae` for FS-UAE, `/usr/share/sounds/sf2/FluidR3_GM.sf2` for FluidSynth.
- Expose typed accessors keyed by emulator/sidecar name.

**Done when:** A test loads a config that overrides only the FluidSynth soundfont path and confirms all other values remain at defaults.

### Task 3.2: DOSBox-Staging launch composition

Build the launch command for DOS games per ADR-0002.

- Inputs: catalog entry, installation record, user config.
- Compose the autoexec from `runtime.dosbox.entry`, `runtime.dosbox.mount`, and `install_path`.
- Compose final config either via temp file or `-c` flags (implementer's call; the test should verify the resulting DOSBox invocation, not the mechanism).
- Honor `--dry-run` flag: print the exact command that would be executed and return without launching.

**Done when:** `reliquaint run qfg1-ega --dry-run` prints a complete, correct DOSBox-Staging invocation against the migrated QFG1 EGA catalog entry and a fixture installation record.

### Task 3.3: FS-UAE launch composition

As 3.2 but for Amiga.

- Inputs: catalog entry, installation record, user config.
- Resolve floppy disk paths against `install_path`.
- Use shipped `.fs-uae` config if present; otherwise apply the model template.
- Honor `--dry-run`.

**Done when:** `reliquaint run fatman --dry-run` prints a complete, correct FS-UAE invocation.

### Task 3.4: Sidecar supervisor

Process supervisor for FluidSynth.

- Lifecycle per `schema.md` §"Sidecar handling": start, supervise, stop on emulator exit.
- Failure to start a sidecar is fatal *only* if the game declares it in `runtime.sidecars`; otherwise a warning.
- Clean shutdown: `SIGTERM` first, `SIGKILL` after a short grace period.

**Done when:** A test launches a `sleep 5` as a sidecar around a `sleep 1` as the emulator and confirms the sidecar is reaped within 1 second of the emulator exiting.

## Milestone 4 — CLI commands

### Task 4.1: `reliquaint list`

Update to use the `CatalogView` from 2.3.

- Default output: tabular, grouped by collection, columns for id, title, year, installed status.
- `--platform dos|amiga` filter.
- `--installed` / `--not-installed` filters.
- `--format json` for scripting.

**Done when:** Manual run against the migrated catalog produces a readable list with installed and not-installed games distinguishable.

### Task 4.2: `reliquaint run <id>`

Wire 3.2 and 3.3 to the CLI.

- Resolve `<id>` against the catalog view.
- If the game has no installation record, exit with an error suggesting `reliquaint install <id>`.
- `--dry-run` preserved.

**Done when:** Migrated games launch via `reliquaint run <id>` and the dry-run output is correct.

### Task 4.3: `reliquaint install <id> <path>`

New subcommand. Creates an installation record for a known catalog entry.

- Validate `<id>` exists in the catalog.
- Validate `<path>` exists and is a directory.
- Run the `[install].expects_files` check from the catalog entry; on failure, list the missing files and ask the user to confirm before writing the record anyway (`--force` flag to skip the prompt).
- Write the installation record per schema.

**Done when:** `reliquaint install qfg1-ega ~/games/qfg1-ega` succeeds against a real install and the resulting record loads correctly into the catalog view.

### Task 4.4: `reliquaint doctor` update

Extend the existing `doctor` subcommand to validate the new model.

- Check emulator binaries resolve.
- Check FluidSynth soundfont exists (if any installed game declares the sidecar).
- Check FS-UAE kickstart_path exists (if any Amiga game is installed).
- Check every installation record's `install_path` exists.
- Check every installation record's `expects_files` are present.
- Surface orphaned installation records.

**Done when:** Running `doctor` on a healthy install reports all-clear; deliberately breaking one of the above produces a clear, actionable error message.

## Milestone 5 — GUI updates

These tasks are roughly sequenced; some can run in parallel with later CLI tasks.

### Task 5.1: Catalog browser view

Replace the current GUI's main view with a browser over the `CatalogView`.

- One card per catalog entry. Show title, year, developer, installed status.
- Group by collection where present.
- Click into an entry to see full metadata, description, acquisition links, install action.
- Use existing Svelte component conventions; do not introduce new component libraries.

**Done when:** Launching the GUI shows every catalog entry with metadata and an obvious distinction between installed and not-installed games.

### Task 5.2: Acquisition link rendering

In the per-entry view, render `[acquisition]` fields as labelled buttons.

- One button per populated field, labels like "Get on GOG", "Get on Steam", "Developer's site".
- Clicking opens the URL in the user's browser (Tauri API).
- Render `acquisition.notes` as plain text below the buttons.

**Done when:** Acquisition links work for QFG1 EGA and at least one Amiga entry.

### Task 5.3: Install workflow (GUI)

A GUI flow that calls into the install logic from Task 4.3.

- "Install" button on a not-installed entry opens a directory picker.
- After selection, run the `expects_files` check; if any are missing, show a confirmation dialog listing what's missing before proceeding.
- On success, refresh the catalog view to reflect installed state.

**Done when:** An end-to-end GUI install of a known game produces a working installation record and the game launches via the GUI's launch button.

### Task 5.4: Launch from GUI

The "Launch" button on an installed entry invokes the same launch path as `reliquaint run <id>`.

- Show emulator stdout/stderr in a collapsible panel for diagnostics.
- Wire the panel to the Tauri-side subscriber layer from Task 1.1 so launcher log events appear alongside the emulator's own output, with level-based color or formatting.
- Disable the launch button while the emulator is running.

**Done when:** Launching from the GUI works for both DOS and Amiga games, and the diagnostic panel surfaces both emulator output and launcher log events for a failed launch attempt.

## Milestone 6 — Migration

The cutover. Once these are done, the v0.1 user can launch games as before through the new model.

### Task 6.1: Stand up the bundled tap directory

Create the bundled tap directory inside the repo. Suggested location: `tap/` at the repo root; final location is the implementer's call but should follow the structure in `schema.md` §"Tap layout".

- Write `tap/tap.toml` with id `reliquaint-core`.
- Create empty `tap/catalog/dos/` and `tap/catalog/amiga/` directories.
- Update the path constants in Task 1.6 to find the bundled tap at this location.

**Done when:** `reliquaint list` runs against the empty bundled tap and reports zero entries without errors.

### Task 6.2: Migrate Quest for Glory manifests

Convert each `dos/quest-for-glory/manifests/*.toml` to the new catalog entry schema and copy to `tap/catalog/dos/<id>.toml`. For each game's `.conf`, copy to `tap/catalog/dos/<id>.conf` and **strip the `[autoexec]` section**, capturing the entry-point command (typically the `.BAT` or `.EXE` invoked) into the catalog entry's `runtime.dosbox.entry` field.

Populate `[meta]`, `[acquisition]`, and `[install].expects_files` for each game using publicly available release information.

**Done when:** All QFG games launch via `reliquaint run <id>` against the new tap, and the original `dos/quest-for-glory/manifests/` directory is removed.

### Task 6.3: Migrate King's Quest manifests

Same as 6.2, for `dos/kings-quest/manifests/*.toml`.

### Task 6.4: Migrate Amiga manifests

Same as 6.2, for `amiga/manifests/*.toml`. For Fatman in particular, populate `runtime.fs_uae.model` and (if known) `runtime.fs_uae.floppies`.

If WHDLoad-only games exist in the current set, document them as deferred-to-v0.2 and skip migration.

### Task 6.5: Migrate user state

A one-time migration helper (CLI command, e.g. `reliquaint migrate-installs`).

- Scan well-known existing paths (`~/games/<id>/`) for each catalog entry.
- For each match, create an installation record without prompting unless the path is ambiguous.
- Print a summary at the end.

**Done when:** A user with the prior layout runs `reliquaint migrate-installs` once and all their previously working games show as installed in `reliquaint list`.

### Task 6.6: Delete or relocate dead code

After migration, prune what's no longer needed.

- Remove the per-collection `manifests/` directories.
- Move `dos/quest-for-glory/scripts/extract-installers.sh` to a sensible location (perhaps `scripts/` at repo root) since it's still useful but no longer collection-scoped.
- Leave the collection guide markdown (`dos/quest-for-glory/quest-for-glory.md` etc.) in place for now; they become future companion content in v0.4 and don't block v0.1.

## Milestone 7 — Documentation

### Task 7.1: Rewrite the README

The repo's README currently describes a docs-and-scripts project. Rewrite as the front door for Reliquaint-the-launcher.

- Open with the project name, the portmanteau callout, the one-line pitch.
- Sections: What it is, Status (pre-v0.1), Installing the launcher, Adding a game you own, Browsing the catalog, Contributing a catalog entry, License.
- Reference `docs/prd.md`, `docs/schema.md`, and the ADRs as further reading.

### Task 7.2: Update `AGENTS.md` and `CLAUDE.md`

Bring both files in line with the new repository structure.

- New directory layout (tap-based).
- New command names (`reliquaint` instead of `classic-launcher`).
- New convention notes (catalog entry locations, installation record locations).
- Remove now-obsolete guidance about the per-collection `manifests/` directories.

### Task 7.3: Write `CONTRIBUTING.md`

A new top-level file covering:

- How to add a catalog entry (PR a TOML file into `tap/catalog/<platform>/`).
- How to test locally (install the launcher, point a test install at game files, verify launch).
- Style conventions (snake_case TOML keys, lowercase-hyphenated ids, etc.).
- The non-acquisition stance: contributors do not link to or host game binaries.

### Task 7.4: Choose and apply a license

The PRD flags this as open. Pick one (likely GPLv3 or MPL-2.0 for code; CC-BY-SA-4.0 for catalog content), add `LICENSE` and `LICENSE-CONTENT` files, reference both in the README.

## Out of scope for v0.1

Documented here so reviewers and contributors can redirect noise:

- Tap subscription / multi-tap support (v0.3).
- Companion content rendering (v0.4).
- WHDLoad and hard-drive Amiga support.
- ScummVM backend.
- Manifest creation wizard for unknown games (v0.2).
- Cross-platform support beyond Linux.
